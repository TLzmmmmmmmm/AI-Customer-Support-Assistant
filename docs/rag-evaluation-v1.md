## 1. 方法：分别检查检索、生成与失败位置

正式运行使用实际生产路径：`POST /api/chat-stream` → 当前Retriever → Context Builder → RAG prompt → DeepSeek → NDJSON delta/done/error。检索只使用最后一条用户问题；这些案例均为单轮，未测多轮指代与历史策略。运行不引入judge模型、重排、query rewriting、BM25、阈值、claim checker或citation功能。

检索以最小必要chunk集合为gold；Hit@5判断至少命中一条，Recall@5为命中必要chunk数/必要chunk总数，First Relevant Rank按生产最终返回顺序。系统事实与chunk证据分开，没有gold的题不硬算检索分数。

生成按0/1/2分别评价正确性、Groundedness、完整性、拒答质量；N/A注明原因并排除相应分母，不合成总分。Groundedness只认可实际provider messages中的可信检索证据和公司系统事实，不能用未传入的知识补足依据。幻觉独立记有无；没有编造参数不等于抵抗注入成功。

评分依据语义而非逐字匹配：允许正确的咨询建议和重复总结；未知要明确说明、不能猜测；英文提问须全英文，公司正式英文名和品牌名须准确。是否提到参考答案中的每一个辅助事实，不等同是否完整回答了用户所问。

受控评测保留query、Top-K、来源、实际context、provider请求和回答，用于逐层核查；没有采集生产用户对话或新增production retrieval日志。
